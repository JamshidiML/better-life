## Classification And Evidence Boundary

This document uses: `Source-verified fact`, `Evidence-supported conclusion`, `Repository decision`, `Founder decision`, `Founder decision pending`, `Design requirement`, `Proposed control`, `Hypothesis`, `Platform limitation`, `Open question`, `Executed test result`, and `Arithmetic check`.

- Executed test result: official vendor, platform, app-store, and organization pages were reviewed for this snapshot.
- Executed test result: no product was installed, purchased, subscribed to, configured, bypass-tested, removed, or used with sensitive data.
- Design requirement: an official vendor page supports only what the vendor currently says about positioning/capability; it does not prove behavior, safety, privacy, accessibility, efficacy, or comparative superiority.
- Design requirement: an app-store listing is additionally mediated by the store and remains listing-stated evidence.
- Design requirement: official platform documentation is evidence of documented platform behavior and limitations, not proof of a third-party product's implementation.
- Open question: all dynamic facts require a dated refresh before product, financial, outreach, or public decisions.

## Reproducible Search Protocol

| Element | Cycle 2 protocol |
| --- | --- |
| Research question | Which current solution families can substitute for one or more Better Life Protection Stack layers, planning/support functions, or professional routes? |
| Sample frame | Browser blocker; multi-device blocker; friction/self-binding; specialist blocker/accountability; OS first-party control; family/managed account control; DNS/router/network filter; DIY/open-source; private planning/education; chosen ally; professional care; mutual aid; no tool. |
| Search terms | Family name plus `official`, `features`, `platforms`, `privacy`, `pricing`, `remove`, `uninstall`, `support`, `terms`; platform and organization names were searched directly. |
| Preferred sources | Current official help/developer/policy pages; then official app-store listings. Independent trials/security studies would be separate evidence and were not systematically searched here. |
| Inclusion | A current official page documents a capability, role, or substitute relevant to the sample frame; source and limitation can be recorded. |
| Exclusion | Affiliate lists, unsourced rankings, copied marketing, inaccessible claims, individual reputation, and entities presented as partners without contact. |
| Deduplication | One row per distinct product/family and architecture role; multiple pages support one row where needed. |
| Extraction | Layer, scope, control model, recipient/admin role, platform limits, data questions, price model category, source type, hands-on state, and Better Life decision question. |
| Verification state | Official-source desk review only. `Hands-on pending` means every behavioral/privacy/cancellation conclusion remains open. |
| Refresh trigger | Before external publication, budget/purchase, outreach, product positioning, or after material source/platform change. |

## Source-Type Separation

| Evidence type | Permitted conclusion | Prohibited conclusion in Cycle 2 |
| --- | --- | --- |
| Vendor/help page | The vendor currently states/describes the cited feature, scope, term, or price category. | Feature works as described; safer/private/effective; complete platform coverage. |
| App-store listing | The listing currently presents the cited claim/capability in that store/region. | Independent verification, durable price/availability, policy implementation. |
| Platform owner documentation | The platform documents the cited API/control/limit. | Third-party integration is correct, approved, safe, or accepted. |
| Privacy policy/terms | The text states the cited contractual/data position. | Actual data flow, compliance, deletion success, security, or comprehension. |
| Independent study/security test | Study result within exact population/version/method limits. | Universal or current product truth without replication/refresh. |
| Hands-on test | Observed result for exact build, account, region, device, scenario, and date. | General behavior outside tested matrix. |
| User report/interview | Participant experience and meaning under consent. | Population prevalence, efficacy, or vendor fact. |

## Frozen Hands-On Protocol For Future Approval

No testing is authorized by this document. If founder budget, legal terms, test-account isolation, and sensitive-data protocol are approved, each selected product uses synthetic domains/content and records:

1. Build/version, country/store, price/trial/tax, account and device matrix.
2. Setup steps, permissions, data disclosures, defaults, admin/ally role, and consent/notice.
3. Supportive/friction/strict behavior, scope, schedules, exceptions, cooling-off, and exact change/cancel flow.
4. False block, false negative, alternate browser/profile/device/network, VPN/DoH, offline, and degraded behavior.
5. Lost credential/device, hostile/unavailable partner, essential access, accessibility, and coercion scenarios.
6. Data inventory from lawful observation, privacy/terms/processors/SDK review, export/delete, uninstall, reinstall, backup/restore, cancellation, and residuals.
7. Claims/pricing copied verbatim only within copyright limits, then classified as vendor-stated or independently supported.
8. No real explicit content, personal browsing, participant account, real ally, or vulnerable-person data.

## Comparative Questions, Not Positioning Claims

| Better Life question | Required comparator | Falsification / exit |
| --- | --- | --- |
| Does Supportive mode add value? | Paper/private plan, reminder, one sec-style friction, no tool. | Remove if no incremental agency/usefulness or greater burden/shame. |
| Does Friction add value? | OS Screen Time, browser blockers, Freedom-style blocker, DIY controls. | Do not build if substitutes meet need more simply/safely. |
| Does Strict add value? | First-party/managed controls, DNS/network and specialist blockers. | Exclude if safe recovery/teardown cannot match benefit or control needs external authority. |
| Is local/accountless meaningful? | Browser-only/open tools, OS controls, local paper plan. | Do not claim differentiation if implementation still depends on cloud/telemetry or users do not value it. |
| Is ally support safer than accountability? | No ally, chosen message, accountability/reporting products. | Remove authority if coercion/regret outweigh incremental support. |
| Is domain-specific education useful? | General journaling, qualified care, mutual aid, no product education. | Route elsewhere if product content adds no safe, evidence-bounded value. |

Repository decision: no `more private`, `safer`, `harder to bypass`, `evidence-based`, `clinically effective`, or `better` competitor claim is supported by this desk review.
